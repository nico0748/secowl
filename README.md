# SecOwl — 脆弱性調査支援アプリケーション

偵察・列挙 → 脆弱性調査 → トリアージ → 調査報告書 の流れを、ローカルの Markdown で記録するアプリです。
データベースは使いません。すべての記録は 1 件 1 ファイルの `.md` として保存先フォルダに置かれます。
同じフォルダを Obsidian の vault として開けば、アプリと Obsidian の双方から同じファイルを読めます。

---

## 起動

ブラウザで使う場合:

```bash
npm install
npm start          # ビルドしてサーバを起動します → http://127.0.0.1:5174
```

デスクトップアプリとして使う場合:

```bash
npm install
npm run app        # ビルドして Electron のウィンドウを開きます
```

配布できる `.app` / `.dmg` を作る場合（macOS でのみ実行できます）:

```bash
npm run dist:mac   # release/ に .dmg が出ます
```

署名と公証は行いません。初回起動時は Finder で右クリック →「開く」を選んでください。
他の人に配るなら Apple Developer Program（年 99 米ドル）での署名が必要です。

開発中は次のコマンドを使います。Vite の開発サーバ（5173）が API を 5174 へ転送します。

```bash
npm run dev        # http://127.0.0.1:5173
```

### デスクトップ版とブラウザ版の違い

中身は同じです。Electron のメインプロセスが同じ Express サーバを立ち上げ、その URL をウィンドウへ読み込ませています。
ポートは OS が空いているものを選ぶため、他のアプリと衝突しません。

デスクトップ版だけで使えるもの:

- 保存先を Finder のダイアログから選べます（「設定」画面の「参照…」）
- 「設定」画面の「Finder で開く」と、メニューの「ファイル → 保存先フォルダを開く」
- 日本語のメニューバーと `Cmd+P`（印刷 / PDF に保存）
- ウィンドウの位置とサイズを次回起動時に復元します
- 「実行」画面（用意したコマンドのテンプレートから、許可したツールを起動します。下の「コマンドの実行」）

保存先の既定値は、ソースから起動したときは `<app>/data`、`.app` から起動したときは `~/Documents/SecOwl` です。
`.app` の中身は書き換えられないため、設定ファイルはアプリのユーザーデータ領域に置きます。

### 保存先

調査データはアプリ直下の `data/` に保存します。初回起動時に作られます。

```
~/Programming/secowl/
├── server/ src/ templates/ …   アプリのコード（Git で追跡）
└── data/                       調査データ（アプリの Git では追跡しない）
    └── <診断対象名>/
```

`data/` はアプリのリポジトリでは `.gitignore` の対象です。調査データを版管理するときは、
`data/` 自体を独立したリポジトリにしてください（「設定」画面の「リポジトリを初期化」が同じことをします）。
入れ子になりますが、外側からは無視されるため衝突しません。アプリと調査データを別々の履歴として扱えます。

別の場所に置きたい場合は、次のどちらかで上書きできます。

```bash
SECOWL_DATA=~/secowl-data npm start
```

アプリの「設定」画面でパスを入力すると、`secowl.config.json` に書き込みます。
このファイルは端末ごとに異なるため、`.gitignore` の対象です。

### モックデータ

画面の動きを確かめるためのデータを作れます。値はすべて架空です。

```bash
node scripts/seed-mock.js          # 診断対象2件（進行中の EC サイト診断 / 完了済みの API 診断）
node scripts/seed-mock.js --reset  # 同名の診断対象を消してから作り直す
```

## MCP 連携

SecOwl の操作を MCP サーバとして公開します。Claude Desktop や Claude Code から、診断対象の作成からレポート生成までを呼び出せます。
サーバは保存先の Markdown を直接読み書きするため、**アプリが起動していなくても動きます**。

```bash
npm run mcp          # 動作確認（stdio で待ち受けます。Ctrl+C で終了）
```

### 登録

アプリの「設定」画面に「MCP 連携」の節があります。そこに出る設定をコピーして登録してください。
`node` の絶対パスと保存先が埋まった状態で出るので、そのまま貼り付けられます。

Claude Desktop は設定ファイルの `mcpServers` に追記して再起動します。

```json
{
  "mcpServers": {
    "secowl": {
      "command": "/usr/local/bin/node",
      "args": ["/Users/you/Programming/secowl/mcp/server.js"],
      "env": { "SECOWL_DATA": "/Users/you/Programming/secowl/data" }
    }
  }
}
```

Claude Code は端末で 1 行です。

```bash
claude mcp add secowl -e SECOWL_DATA=<保存先> -- <node のパス> <アプリ>/mcp/server.js
```

### 環境変数

| 変数 | 内容 |
|---|---|
| `SECOWL_DATA` | 調査データの保存先。省略するとアプリの設定か既定値を使います |
| `SECOWL_CONFIG` | 設定ファイルのパス |
| `SECOWL_MCP_READONLY` | `1` にすると読み取り専用の 23 ツールだけを公開します |

**書き込みを許すと、接続したモデルが発見事項や報告書を直接書き換えられます。** 読ませるだけなら
`SECOWL_MCP_READONLY=1` を付けて登録してください。設定画面のチェックを入れると、その状態の設定が出ます。

### 公開するツール（39）

**読み取り（23）**

`list_engagements` / `get_engagement` / `get_dashboard` / `get_progress` / `list_surfaces` /
`list_tool_logs` / `list_findings` / `get_checklist` / `list_evidence` / `read_doc` / `search` /
`get_report` / `get_settings` / `git_status` / `git_log` / `list_reference_tools` /
`get_reference_tool` / `list_usecases` / `get_usecase` / `list_playbook` / `get_playbook` /
`calculate_cvss` / `check_report`

**書き込み（16）**

`create_engagement` / `update_engagement` / `create_surface` / `create_tool_log` / `create_finding` / `update_doc` /
`set_checklist_item` / `import_tool_output` / `add_evidence` / `delete_evidence` / `build_report` /
`export_report` / `ensure_docs` / `set_data_root` / `git_init` / `git_commit`

`get_progress` はフェーズごとの状態と不足を返し、`get_playbook` はそのフェーズの手順書を返します。
何をすべきか迷ったときは、この 2 つを続けて呼ぶと判断できます。

`export_report` は docx / 共有バンドル HTML / 印刷用 HTML / Markdown を書き出し、保存したパスを返します。
`import_tool_output` は `dry_run` を付けて先に件数を確認できます。
`build_report` は下書き（draft）を報告書に含めず、含めた件数（`included`）と除外した下書き（`excluded`）を返します。
`update_engagement` は診断対象の名前・顧客・対象システム・期間を `engagement.json` に保存し、スコープ文書と報告書の frontmatter にある写しを同期します。
`check_report` は共有の前に、報告書に載せる個票に伏せていない Cookie・Authorization・JWT・メールアドレスが残っていないかを点検します。

### リソースとプロンプト

リソースは `secowl://engagements`、`secowl://<診断対象 ID>/summary`、`secowl://<診断対象 ID>/report` の 3 種です。
プロンプトは「発見事項をトリアージする」「報告書の総評を書く」「偵察の次の一手を決める」の 3 つを用意しています。

### サーバの指示

接続したモデルには、サーバから次の方針を渡しています。

- 自動検出の結果をそのまま confirmed にしない。手動で裏取りしてから状態を変える
- 証跡や本文に実トークン・個人情報を書かない
- 報告書を読む前に `build_report` を実行すると最新の発見事項が反映される

## 画面と記録の対応

| 画面 | 役割 | 生成される Markdown |
|---|---|---|
| ホーム | 調査状況の集計を表示します | （集計のみ。ファイルは作りません） |
| 偵察 | サブドメイン・ホスト・ポート・エンドポイントを登録します | `10-偵察/srf-XXXX-<名前>.md` |
| 調査 | ツール実行ログとチェックリストを扱います | `20-調査/logs/log-XXXX-<名前>.md` |
| トリアージ | 発見事項個票を起票し、CVSS と深刻度を決めます | `30-トリアージ/fnd-XXXX-<名前>.md` |
| 報告書 | 発見事項を統合した診断報告書を組みます | `40-報告/診断報告書.md` |
| ツール | 診断で使うツールの手引きとユースケース | （読み取りのみ。`knowledge/` の Markdown） |
| 進め方 | E0 から E4 までの標準手順書 | （読み取りのみ。`knowledge/playbook/` の Markdown） |

診断対象を作ると、次の構成が保存先に生成されます。

```
<保存先>/<診断対象名>/
├── engagement.json        診断対象のメタ情報
├── 00-診断対象/
│   ├── スコープとRoE.md    E0 事前準備
│   └── 進め方.md          E0 から E4 までの手順と完了条件
├── 10-偵察/               サーフェス 1 件につき 1 ファイル
│   └── 攻撃面マップ.md     E1 の成果物。全体像と優先順位
├── 20-調査/
│   ├── チェックリスト.md   OWASP WSTG v4.2 / Top 10:2025 準拠
│   ├── 未検出記録.md       検証したが検出に至らなかった記録
│   └── logs/              ツール実行ログ 1 件につき 1 ファイル
├── 30-トリアージ/          発見事項個票 1 件につき 1 ファイル
└── 40-報告/
    └── 診断報告書.md
```

旧バージョンが作った `00-案件/` のデータも、そのまま開けます。
以前に作った診断対象へあとから追加分を補うには、設定画面の「テンプレートを補う」を押すか、
MCP の `ensure_docs` を呼びます。既にあるファイルは変更しません。

## 進め方（標準手順書）

診断対象を作ると、ホーム画面の先頭に「進め方」が出ます。E0 事前準備から E4 報告までの
5 フェーズについて、目標・着手順・完了条件を示し、データから導いた状態（未着手・進行中・完了）と
「次の一手」を添えます。

| | フェーズ | 完了条件 |
|---|---|---|
| E0 | 事前準備 | スコープと RoE に書面の承認がある |
| E1 | 偵察・列挙 | 攻撃面の一覧がそろい、入力点を棚卸しした |
| E2 | 脆弱性調査 | チェックリストの全項目が「検出有」か「検出無」になった |
| E3 | 検証・トリアージ | 全発見事項に再現手順・証跡・CVSS・修正案がそろった |
| E4 | 報告 | 二層の読み手に書き分けた報告書を納品した |

偵察・調査・トリアージ・報告書の各画面には、そのフェーズの手順パネルが付きます。
着手順の各手順には、そこで使うツールへのリンクが並びます。全文は「進め方」画面（`/playbook`）で読めます。

内容は `knowledge/playbook/*.md` が原本です。frontmatter に手順・完了条件・つまずきやすい点を書き、
本文に技法の詳細を書きます。手元で書き足せます。

トリアージの手順書には、CVSS v3.1 の付け方と、**STRIDE と DREAD をどう扱うか**を書いています。
発見事項のスコアリングには CVSS v3.1 を使い、STRIDE は網羅性の点検に使い、DREAD は再現性がないため
納品物では使いません。

## ツールリファレンス

「ツール」画面に、診断で使うツールの要点と、使う順番をまとめた手引きを置いています。
中身は `knowledge/` 配下の Markdown なので、手元で書き足せます。再読み込みは `GET /api/knowledge?reload=1` です。

```
knowledge/
├── tools/      44 件。カテゴリは プロキシ・通信解析 / フィッシング訓練 / 管理アセットの調査 /
│               サブドメイン探索 / ポートスキャン / Webアプリケーションの調査
└── usecases/   7 件。使うツールの順番つきの手引き
```

各ツールのページには、機能・使いどころ・コマンド例・注意点を書いています。
ページを開いた状態で「実行ログに記録」を押すと、**そのページのコマンド例を候補に出した状態で**ツール実行ログを起票できます。

frontmatter の項目:

```yaml
---
name: nmap
category: ポートスキャン
tags: [必修, ポートスキャン]
url: https://nmap.org/
license: NPSL（無償）
phase: [recon, survey]
authorization: 必須      # 書面承認が要るものだけ。画面にバッジが出ます
---
```

ユースケースは次の 7 件です。

| ファイル | 内容 |
|---|---|
| `01-recon-kickoff` | 新規ドメインの偵察を一から立ち上げる |
| `02-login-assessment` | ログイン機能を診断する（認証・セッション・認可） |
| `03-api-authorization` | API の認可を検証する |
| `04-phishing-exercise` | フィッシング訓練を実施する |
| `05-asset-inventory` | 外部公開資産を棚卸しする（ASM） |
| `06-subdomain-takeover` | Subdomain Takeover を探す |
| `07-traffic-analysis` | 通信を捕まえて解析する |

MCP からは `list_reference_tools` / `get_reference_tool` / `list_usecases` / `get_usecase` で読めます。

### アイコン

アイコンは `public/tool-icons/<slug>.png` に固定で置き、静的ファイルとして配信します。
**アプリは実行中に外部へ取得しにいきません。** 同梱しているのはカテゴリ色と頭文字の既定タイルです。

公式サイトの画像に差し替えるときは、保守用スクリプトを **一度だけ** 実行します。

```bash
npm run icons                      # まだ取得していないものだけ
npm run icons -- --force           # すべて取り直す
npm run icons -- --only nmap,httpx # 指定したものだけ
```

取得の優先順位は次のとおりです。

1. 公式サイトの `apple-touch-icon`
2. 公式サイトの `favicon`
3. 公式サイトの `/favicon.ico`
4. 公式サイトの **ホームのカバー画像**（`og:image` / `twitter:image`）

取得できたものは `public/tool-icons/` を上書きし、差し替え前のタイルは `public/tool-icons/tiles/` に退避します。
取得元は `public/tool-icons/manifest.json` に残ります。取得できなかったツールは既定タイルのままです。

**取得後は `public/tool-icons/` をリポジトリにコミットしてください。** 以後は取得なしで表示され、
`npm run build` が `dist/tool-icons/` へ複製します。

### 取り扱いについて

フィッシング訓練のカテゴリに含まれるツールは、**対象組織の書面承認が前提**です。
各ページの冒頭に条件を書いています。承認が要るものには画面にバッジが出ます。

evilginx2 のページは、仕組みと防御側の対策（FIDO2 / WebAuthn への移行）を説明するもので、設定手順は載せていません。

## ホーム画面の集計の出どころ

| 表示 | 集計元 |
|---|---|
| アタックサーフェス TOTAL | `10-偵察/` のファイル数（`in_scope: false` を除く） |
| ポート番号の一覧 | サーフェスの `port` の値ごとの件数。行をクリックすると該当サーフェスへ絞り込みます |
| 連携数 | ツール名ごとの記録数（ツール実行ログ＋そのツールを引用した発見事項） |
| 脆弱性スコア | 発見事項個票の `severity` の件数。カードをクリックすると一覧を絞り込みます |
| テクノロジー | サーフェスの `product` と `tech` の件数。上位 5 件と「その他」を表示します |

深刻度は CVSS 基本値から決まります。区分は FIRST に合わせています。

| 深刻度 | CVSS | 画面表記 |
|---|---|---|
| 緊急 | 9.0 – 10.0 | CRITICAL |
| 重要 | 7.0 – 8.9 | HIGH |
| 警告 | 4.0 – 6.9 | MEDIUM |
| 注意 | 0.1 – 3.9 | LOW |
| なし | 0 | INFO |

「深刻度（手動で上書きする場合）」を選ぶと、CVSS 基本値より優先されます。

## Markdown との往復

- アプリのフォームは frontmatter のキーと、本文の `## 見出し` に対応します。
- 保存すると、対象のキーと見出しだけを書き換えます。アプリが知らないキーと見出しはそのまま残ります。
- チェックリストの切り替えは、該当行の `- [ ]` を `- [x]` に直接書き換えます。
- Obsidian で直接編集したあと、アプリを再読み込みすると変更が反映されます。

### テンプレート

`templates/` に 9 種類のテンプレートがあります。診断対象や記録を作るときに `{{...}}` を置換して生成します。

| ファイル | 用途 |
|---|---|
| `00-スコープとRoE.md` | E0 事前準備。書面承認の記録 |
| `01-進め方.md` | E0 から E4 までの手順と完了条件 |
| `10-サーフェス.md` | 攻撃面 1 件の記録 |
| `11-攻撃面マップ.md` | E1 の成果物。全体像・入力点・優先順位 |
| `20-調査チェックリスト.md` | OWASP WSTG v4.2 / Top 10:2025 準拠の実行チェックリスト |
| `21-ツール実行ログ.md` | コマンドと出力、読み取ったこと |
| `22-未検出記録.md` | 検証したが検出に至らなかった記録。報告書の付録になります |
| `30-発見事項個票.md` | 1 脆弱性 1 票 |
| `40-診断報告書.md` | 納品物。自動生成ブロックを含む |

テンプレートは直接編集できます。既存の記録には影響しません。

これらは Obsidian vault の `_templates/web-pentest-*.md` を土台にしています。
Templater 構文（`<% %>`）をアプリ用の `{{ }}` に置き換え、偵察とツールログの 2 種類を追加しました。

### 報告書の自動生成ブロック

`40-報告/診断報告書.md` には `<!-- vs:name -->` 〜 `<!-- /vs:name -->` で囲んだ区間があります。
「発見事項を反映」を押すと、この区間だけを現在のデータで書き換えます。区間の外に書いた文章は残ります。

| マーカー | 内容 |

| `vs:surface-inventory` | アタックサーフェス一覧 |
| `vs:tools` | 使用したツール |

## 診断対象の情報と事前準備

- 名前・顧客・対象システム・期間の正は `engagement.json` です。スコープ文書と報告書の frontmatter にある `client` / `target_system` / `period_from` / `period_to` は写しで、
  アプリから診断対象の情報を保存したときに同期します。報告書の表紙（印刷・Word）は `engagement.json` を読みます。
- 「事前準備」画面（`/scope`）で、スコープ文書の承認（`agreed`・`agreed_at`・`agreed_by`）を記録します。`agreed: true` でホームの E0 が完了になります。
- Obsidian で写しを直接書き換えた場合、アプリはそれを正とは扱わず、画面で食い違いを知らせます。「設定の値に揃える」で同期し直せます。

## 設計の前提

- サーバは `127.0.0.1` だけで待ち受けます。外部からは接続できません。
- 読み書きの対象は保存先フォルダ配下の `.md` に限ります。それ以外のパスは API が拒否します。
- 認証はありません。1 人で使うことを前提にしています。
- 証跡の実トークンと個人情報は、保存する前にマスキングしてください。
- API は `Host` が `127.0.0.1` / `localhost` / `[::1]` の要求だけを受け付けます（DNS rebinding 対策）。
  書き込みの要求は、`Origin` の host:port が `Host` と一致しない場合と、`Sec-Fetch-Site` が `same-origin` / `none` 以外の場合に拒否します。
  同じ PC の別ポートで動くページからの書き込みも拒否します。`vite --host` などで LAN から開いた場合、API は 403 を返します（意図した動作です）。
- Markdown のプレビューと書き出しでは、生の HTML を描画せず文字として出します。`javascript:` などのリンクはリンクにしません。

## コマンドの実行（デスクトップ版のみ）

左のレールの「実行」から、`knowledge/tools/*.md` の `commands:` に書いたテンプレートを実行します。ブラウザ版ではルート自体が存在せず（404）、画面にも出ません。

- 許可したプログラムだけ（nmap・httpx・nuclei・ffuf・gobuster・subfinder ほか。`curl` と `sudo` は入れていません）。シェルは使わず、引数の配列をそのまま渡します。値が `-` で始まるものは拒否します
- 実行前に、対象の正規化した値をスコープ（`scope_targets` / `scope_allow` / `scope_deny` / `scope_ports`）に照らし、書面の承認（承認印・承認日・承認者）と診断期間を確認します。起動の直前にも、もう一度確認します
- 「実行前の確認」で、実行ファイルの絶対パスと引数を 1 つずつ見せます。「実行」を押すと、アプリ本体からも短いネイティブの確認が出ます（既定はキャンセル）。起動は HTTP ではなく IPC だけです
- 出力ファイルは `<診断対象>/20-調査/取得データ/` の中だけ。**この生の出力は伏せ字にしておらず、Git でも追跡しません。** ツール実行ログに書く本文は、制御文字を除き、Cookie・トークン・JWT・メールアドレスを伏せ字にしてから保存します
- ツール実行ログに保存する本文は、先頭と末尾（それぞれ約 100KB）だけです。1 行が 32,000 文字を超えるときは、先頭を残して「長すぎる行の途中を省略しました（N 文字）」と書きます。切れた秘匿値の一部が残らないよう、区切りのところまで戻して切ります
- 実行の記録は `<診断対象>/.secowl/audit.jsonl` に追記します（各行に前の行のハッシュを持たせ、書き換えると分かります）。実行ページの「実行の履歴」の「実行の記録を検証」で、つながりを確かめられます
- 保存先の `.gitignore` には `*/20-調査/取得データ/` と `*/.secowl/run/` を入れます。以前に作った保存先や、自分で `git init` した保存先には、設定画面の Git の警告から追記できます（コミットするときにも、足りなければ追記します）。すでに追跡されているファイルは `.gitignore` では外れないため、設定画面に件数を出して知らせます
- 実行ファイルは `/opt/homebrew/bin`・`/usr/local/bin`・`~/go/bin`・`~/.local/bin` と `PATH` から探します。他のユーザーが書き換えられる権限のものは実行しません（実体だけでなく、見つけた場所と、リンクをたどった道筋のディレクトリも見ます。たとえば Intel 版 Homebrew の `/usr/local/bin` が既定でグループに書き込みを許している場合は、そこから見つけたものは実行不可と表示されます。`chmod go-w /usr/local/bin` で直すか、`~/go/bin` や `~/.local/bin` に置いてください）。子プロセスの環境は PATH・HOME・LANG などに絞ります（プロキシを通すときだけ `secowl.config.json` に `"execPassProxy": true`）。同時に実行できる数は `execConcurrency`（既定 2）

画面（HTML・JS・CSS）には、自分のオリジンのスクリプトだけを許す CSP（`script-src 'self'`）を付けています。テーマの先読みスクリプトも外部ファイル（`theme-init.js`）にしてあります。このため、Markdown 本文に埋め込んだ**外部ドメインの画像**は読み込まれません（`img-src` は自分自身・`data:`・`blob:` だけ）。診断中に外部へ接続しないための意図した挙動です。画像は保存先の中に置いてください。

テンプレートを足すときの注意:

- 変数 1 つは引数 1 個です。空のまま引数を省く書き方はないので、`required: false` にするときは `default` が必要です（読み込み時に検査します）
- ffuf / gobuster のワードリストは、`/usr/share`・`/usr/local/share`・`/opt/homebrew/share`・`/opt`・自分のホームフォルダ（`/Users/<名前>`、`/home/<名前>`）の直下にある `wordlists`・`seclists`・`SecLists`・`dirb`・`dirbuster` の下の `.txt` / `.lst` だけです。ほかの場所のファイルや `..` は通しません（独自のワードリストは `~/wordlists/` に置くと使えます）

Electron での実機確認は `xvfb-run -a node test/e2e/runner.e2e.cjs`（Playwright が必要。`npm test` には含めません。本物のツールは使わず、代役のプログラムを使います）。

## ツール出力の取り込み

「偵察」画面の「ツール出力を取り込む」から、各ツールの出力を貼り付けます。形式は内容から判定します。

| 形式 | 取り込み元の例 | 生成されるもの |
|---|---|---|
| nmap XML | `nmap -sV -oX scan.xml <対象>` | ホストと開いているポートのサーフェス |
| httpx JSONL | `httpx -json` | エンドポイントのサーフェス（技術スタック付き） |
| nuclei JSONL | `nuclei -jsonl` | サーフェスと、draft 状態の発見事項 |
| サブドメイン一覧 | subfinder / amass の JSON、1 行 1 ドメインのテキスト | サブドメインのサーフェス |
| ffuf JSON | `ffuf -o result.json -of json` | エンドポイントのサーフェス |
| gobuster | `gobuster dir` の標準出力 | エンドポイントのサーフェス |

「内容を確認」を押すとファイルを書かずに件数と一覧だけを出します。内容を見てから「取り込む」を押してください。

同じ値のサーフェスがすでにある場合は、新規に作らず既存ファイルの `discovered_by` と `tech` に追記します。
サブドメインとホストは同じ対象を指すことがあるため、値が一致すれば同一として扱います。

nuclei から起票した発見事項は `status: draft` で、本文に「手動で裏取りしてください」と書き込みます。
自動検出をそのまま報告書へ載せないための措置です。

## CVSS 計算機

発見事項個票の「CVSS 計算機」から開きます。

- **v3.1**: 基本評価・現状評価・環境評価を計算します。式は FIRST の仕様書 (CVSS v3.1 Specification Document §7) のとおりです。
  既知のベクタ 10 件で基本値を検算してあります。「基本値を個票へ反映」を押すとベクタとスコアが個票に入り、深刻度が決まります。

### 深刻度の決まり方（`severity_source`）

個票の frontmatter の `severity_source` は、深刻度を CVSS 基本値から決めたか（`cvss`）、手で決めたか（`manual`）を表します。
キーがない既存の個票は `cvss` とみなします。

- 基本値（`cvss_score`）を入れると、深刻度は FIRST の区分で決まります。
- 「深刻度」で基本値から導いた値と**異なる**値を選ぶと `manual` になり、あとで別の欄を保存しても上書きは残ります。
  「CVSS 基本値から決める」を選ぶと `cvss` に戻ります。
- 基本値が未記入のあいだは、選んだ深刻度（nuclei の取り込みでは nuclei の深刻度）を仮の値として使います。基本値を入れた時点で基本値から決まります。
- **v4.0**: ベクタ文字列の組み立てだけを行います。v4.0 のスコアは MacroVector の参照表を使うため、本アプリでは計算しません。
  スコアは [FIRST の計算機](https://www.first.org/cvss/calculator/4.0) で算出し、個票へ手入力してください。

## 証跡とマスキング

発見事項個票の右側のパネルで扱います。画像は診断対象フォルダの `evidence/` に保存します。

- 画像を選ぶとアップロードします。ファイル名には発見事項 ID が前置されます。
- 「マスキング」で画像を開き、隠したい範囲をドラッグすると塗りつぶします。保存は画素を上書きするため、元の内容は残りません。
- 個票を開いている間は、画像を貼り付ける（⌘V / Ctrl+V）か、パネルへドロップすると証跡として保存します。
  貼り付けた画像は、入力中の見出し（なければ「発見場所」）にリンクを挿入します。
- 「リクエスト / レスポンス」の「HTTP を貼り付け」では、Cookie の値・Authorization・JWT・API キーやトークンやパスワード（`X-Api-Key` ヘッダ、`access_token=`、JSON の `"token"` など）・メールアドレスと、指定した語句を `[REDACTED]` に置き換えてから、コードブロックで追記します。
- 本文に伏せていない Cookie・Authorization・JWT・API キー／トークン／パスワード・メールアドレスが残っていると、個票の上と共有ダイアログに警告を出します（`example.com` などの例示用ドメインと、`...`・`█`・`[REDACTED]` などで伏せた値は数えません）。
- 「本文へ挿入」で `![証跡](../evidence/<ファイル名>)` を「発見場所」の節に追記します。保存すると Markdown に入ります。
  個票は `30-トリアージ/` にあるため、Obsidian でも個票の位置から解決できる相対パスにしています。
  旧形式の `evidence/<ファイル名>` もアプリのプレビューと書き出しでは表示します（Obsidian での表示は環境によります。未検証）。

## Git（保存先の版管理）

「設定」画面から扱います。保存先フォルダそのものをリポジトリにします。

- 「リポジトリを初期化」で `git init` と `.gitignore` の生成を行います。
- `.gitignore` は既定で `*/evidence/` を除外します。証跡にマスキング漏れが残ると履歴から完全には消せないためです。
  追跡する場合は初期化時にチェックを入れてください。
- 未コミットの変更を一覧で確認し、メッセージを付けてコミットできます。直近 10 件の履歴も表示します。

リモートへの push はアプリから行いません。`git remote add` と `git push` は端末で実行してください。

## 共有と書き出し

「報告書」画面の「共有・書き出し」から選びます。

| 形式 | 用途 | 特徴 |
|---|---|---|
| 共有バンドル（HTML 1 ファイル） | 調査結果を他の人に渡す | 自己完結。ブラウザで開くだけ。深刻度での絞り込み付き。書き込みはできない |
| 印刷用レイアウト | PDF にして納品する | 表紙・目次・改ページ付き。ブラウザの印刷から PDF に保存する |
| Word (.docx) | 納品や社内レビュー | 表紙と本文を含む。見出し・表・コード・画像に対応 |
| Markdown | 他のツールへ渡す | 報告書ファイルをそのまま書き出す |

共有バンドルには次の選択肢があります。

- **draft 状態の発見事項も含める**: 既定では裏取り前（draft）の発見事項を除きます。社内レビューでは含めてください。
- **証跡画像を埋め込む**: 画像を data URL として埋め込みます。1 ファイルで完結しますが、サイズが増えます。

共有バンドルは機密情報を含みます。渡す前に証跡のマスキングを確認してください。
