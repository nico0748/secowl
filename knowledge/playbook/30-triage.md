## CVSS v3.1 の付け方

計算には FIRST の定義をそのまま使います。SecOwl の発見事項個票にある CVSS 計算機で、ベクタとスコアを同時に残せます。

| 評価項目 | 何を見るか | よくある判断 |
|---|---|---|
| AV 攻撃元区分 | どこから攻撃できるか | インターネット越しに到達できるなら `N` |
| AC 攻撃条件の複雑さ | 攻撃者の制御外の条件が要るか | 特別な条件が不要なら `L` |
| PR 必要な権限 | 攻撃に必要な最低権限 | 未認証で到達できるなら必ず `N` |
| UI 利用者の関与 | 被害者の操作が要るか | 他人に踏ませる必要があるなら `R` |
| S スコープ | 影響が別の管理主体へ及ぶか | 管理者セッションを奪うなど境界を越えるなら `C` |
| C / I / A | 機密性・完全性・可用性への影響 | 観測できた範囲だけで決める |

### 判断の原則

1. 観測した事実だけで決めます。推測で上げません。
2. 到達性を最優先で見ます。未認証で到達できるものは、同じ技術的影響でも上に来ます。
3. 迷ったら低いほうへ倒し、理由を書きます。
4. 同じ性質の発見事項には、同じ基準を適用します。

### 深刻度の区分

| 深刻度 | スコア |
|---|---|
| 緊急 Critical | 9.0 – 10.0 |
| 重要 High | 7.0 – 8.9 |
| 警告 Medium | 4.0 – 6.9 |
| 注意 Low | 0.1 – 3.9 |
| なし None | 0 |

### CVSS の数値はリスクではない

Base は環境に依存しない重大度です。実際のリスクは、その資産が何を扱うか、代替手段があるか、業務が止まるかで変わります。報告書では、CVSS と事業影響を分けて提示します。

## STRIDE と DREAD をどう扱うか

結論を先に書きます。**発見事項のスコアリングには CVSS v3.1 を使います。STRIDE は網羅性の点検に使い、DREAD は納品物では使いません。**

| 手法 | 性質 | この診断での使い道 |
|---|---|---|
| CVSS v3.1 | 脆弱性の重大度を、定義済みの基準で数値化する | 発見事項の深刻度。ベクタが残るため第三者が再計算できる |
| STRIDE | 脅威を 6 種に分類する枠組み。設計段階の脅威分析で使う | 調査の抜け漏れ点検。「なりすまし」「改ざん」などの観点で未検証の領域を洗い出す |
| DREAD | 5 項目を各自が 1 から 10 で採点し平均する | 使わない。採点者によって値が変わり、再現性がない |
| OWASP Risk Rating | 発生可能性と影響を分けて評価する | 事業リスクの説明に使う。CVSS の数値を補う文脈として |

### STRIDE を点検に使う

調査の終盤で、6 つの観点に未検証の領域がないかを確かめます。

| STRIDE | 対応する確認 |
|---|---|
| Spoofing なりすまし | 認証（A07）、セッション、JWT |
| Tampering 改ざん | 整合性（A08）、クライアント値の信頼 |
| Repudiation 否認 | ログ・監視（A09） |
| Information Disclosure 情報漏えい | 設定ミス（A02）、暗号化（A04） |
| Denial of Service サービス妨害 | 設計（A06）。ただし実際の負荷試験は行わない |
| Elevation of Privilege 権限昇格 | アクセス制御（A01） |

6 観点のどれかが空白なら、その領域の確認が抜けています。

### DREAD を使わない理由

DREAD は Damage・Reproducibility・Exploitability・Affected users・Discoverability の 5 項目を主観で採点します。同じ脆弱性でも採点者が変わると値が変わるため、納品物の根拠として成立しません。提唱元でも既に推奨されていません。クライアントから DREAD の提示を求められた場合は、CVSS のベクタを添えたうえで補助的に併記します。

## 対応の優先順位の決め方

CVSS だけで並べると、現場で動かせる順番になりません。次の 4 つを合わせて並べます。

| 観点 | 問い |
|---|---|
| 深刻度 | CVSS はいくつか |
| 到達性 | 未認証・外部から到達できるか |
| 影響資産 | 個人情報・認証情報・決済に触れるか |
| 修正コスト | 設定変更で済むか、改修が要るか |

実務では、次の順に並べると説明しやすくなります。

1. 未認証で到達でき、機密情報か認証情報に至るもの
2. 設定変更だけで即日塞げるもの（コストが低く効果が確実）
3. 認証後に成立する越境・ロジックの不備
4. 単独では影響が小さい多層防御の不足（まとめて 1 件にする）

## 同じ問題が複数の対象で出たとき

個票は 1 件にまとめ、対象の一覧に全ホストを並べます。横断事項として報告すると、件数を水増しせずに広がりを示せます。セキュリティヘッダの欠落がその典型です。
