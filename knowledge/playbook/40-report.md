  - title: エグゼクティブサマリを事業の言葉で書く
    detail: 非技術者が読む箇所です。XSS や SQLi といった語をそのまま使わず、何ができてしまうのか、誰にどんな不利益があるのかを書きます。
  - title: 調査概要でスコープと手法を示す
    detail: 対象ホスト、ホスティング構成、URL ルーティング、対象外とした範囲、調査期間と体制、準拠した基準、深刻度の定義を書きます。読み手が結果の射程を判断できるようにします。
  - title: 発見事項一覧で全体像を見せる
    detail: 深刻度別の件数、対象別の件数、横断的に確認された事項を並べます。SecOwl では「発見事項を反映」で自動生成できます。
    doc: report
  - title: 脆弱性の詳細を個票から組む
    detail: 1 件につき、平易な説明・技術的詳細と再現手順・証跡・想定される影響・推奨対応・参考情報を置きます。
  - title: 検証したが脆弱性に至らなかった観点を付録に置く
    detail: 観点ごとに、何をどう確認し、なぜ問題なしと判断したかを書きます。防御が有効に機能していた点も明記します。網羅性の証明になります。
  - title: 深掘りして不発に終わった試行を付録に置く
    detail: 仮説・試したこと・どこで止まったか・そこから分かったことを記録します。止まった位置が、実装されている防御を示します。
  - title: 総括と改善ロードマップを書く
    detail: 構成に起因する所見をまとめ、即日・短期・中期の 3 段で対応順を示します。再診断の推奨時期も書きます。
  - title: 制限事項と免責を書く
    detail: 検証を妨げた要因を書きます。WAF による遮断、検証時間帯の制約、対象外領域、テストデータ不足が該当します。すべての脆弱性がないことの保証ではないと明記します。
  - title: 公開前にマスキングを確認する
    detail: 実トークン・個人情報・内部パスが残っていないかを通読して確かめます。報告書自体が漏えい源になりかねません。

  - 制限事項と免責を書いた

## 二層の読み手に書き分ける

| 読み手 | 読む箇所 | 書き方 |
|---|---|---|
| 経営層・事務担当 | エグゼクティブサマリ、各発見事項の「平易な説明」、総括 | 専門用語を使わない。業務・利用者・信頼への影響で書く |
| 開発・運用担当 | 調査概要、脆弱性の詳細、付録 | 再現できる粒度で書く。入力がどこで受け取られ、どこで出力されるかを示す |

## 推奨する章立て

| 章 | 内容 |
|---|---|
| 表紙 | 機密区分、対象、版、発行日、実施期間、実施者、提出先 |
| 改訂履歴 | 版・日付・変更内容 |
| 1 エグゼクティブサマリ | 目的と背景、総合評価、深刻度別件数、特に注意すべき発見、対応の優先順位 |
| 2 調査概要 | 対象、スコープ、ホスティング構成、URL ルーティング、対象外、調査した利用者視点、期間と体制と手法、深刻度の定義、本書の読み方 |
| 3 発見事項一覧 | 脆弱性サマリ、対象別件数、横断的に確認された事項 |
| 4 脆弱性の詳細 | 発見事項個票 1 件につき 1 節 |
| 5 総括と改善ロードマップ | 総括、構成に起因する所見、改善ロードマップ、再診断の推奨 |
| 6 付録 | 調査手法の詳細、免責事項、用語集、CVSS の補足、検証したが脆弱性に至らなかった観点、不発に終わった試行、受動的偵察の結果、使用ツールと実行環境 |

## 発見事項 1 件に必要な要素

| 要素 | 書くこと |
|---|---|
| 識別情報 | ID、脆弱性名称、深刻度、CVSS スコアとベクタ、CWE、OWASP 分類、WSTG 項目 |
| 対象 | ホスト、URL、発見に必要な立場（未認証・一般・管理） |
| 平易な説明 | 何ができてしまうのか、放置すると誰にどんな不利益があるのか。3 行から 5 行 |
| 技術的詳細 | 発生箇所、原因、観測された挙動。入力の受け口と出力先を明示 |
| 証跡 | リクエストとレスポンスの抜粋、スクリーンショット。機微情報はマスキング |
| 再現手順 | 前提条件から書く。第三者が同じ結果に到達できる粒度 |
| 想定される影響 | 技術的影響と、事業影響への翻訳の 2 段 |
| 推奨対応 | 短期の回避策と恒久対策。どの入力を・どの層で・どう検証するかまで |
| 参考情報 | WSTG の項目、OWASP のチートシート、CWE |

## 「見つからなかったこと」の書き方

検証したが検出に至らなかった観点は、根拠と一緒に残します。

| 判定 | 意味 |
|---|---|
| 検出なし | 検証し、問題を確認しなかった |
| 該当なし | 対象に当該機能が存在しない |
| 未検証 | 制約により検証できなかった。理由を必ず書く |

「検出なし」と「未検証」を混ぜて書かないでください。前者は網羅性の証明になりますが、後者は残課題です。

## 納品物に載せないもの

- 武器化した exploit コード。概念と再現手順にとどめます
- マスキングしていない実トークンと個人情報
- 第三者の個人情報が写り込んだスクリーンショット
