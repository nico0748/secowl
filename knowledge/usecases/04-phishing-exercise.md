> **実施の条件.** 対象組織の書面承認、対象者の範囲、実施期間、停止条件、収集データの種類と保管期間を RoE に明記します。
> 承認のない相手への送信は行いません。

## 0. 合意する内容

| 項目 | 決めること |
|---|---|
| 対象者 | 部署・人数。全社か一部か |
| 題材 | 業務に関係する内容。人事・健康・金銭など心理的負荷の大きい題材は避ける |
| 収集データ | 開封・クリックまでか、入力内容まで記録するか |
| 停止条件 | 業務影響が出た場合に誰がどう止めるか |
| 連絡先 | 情報システム部門・ヘルプデスクへの事前共有の有無 |
| 公表 | 結果を個人別に出すか、部署単位に留めるか |

**個人の成績を評価に使わないことを合意してください。** 報告率を上げたいなら、報告した人を評価する設計にします。

## 1. ドメインを用意する

```bash
# 似たドメインの候補を出し、登録状況を見る
dnstwist --registered --mxcheck --format csv example.com > twist.csv
```

訓練では**自組織が取得したドメイン**だけを使います。他者が登録済みのものは使いません。
同時に、この結果は「第三者に似たドメインを取られていないか」の調査でもあります。取られていればそれ自体が報告対象です。

## 2. 送信側を整える

```bash
# 訓練用ドメインに SPF / DKIM / DMARC を設定し、確認する
dig +short TXT training.example.jp | grep spf1
dig +short TXT _dmarc.training.example.jp
```

設定しないと大半が迷惑メール判定になり、「設計ミスによる低い開封率」を結果として読んでしまいます。

## 3. Gophish で配信する

1. Sending Profile を作り、Send Test Email で自分宛に届くことを確認
2. Email Template を作る。`{{.FirstName}}` `{{.URL}}` `{{.Tracker}}` を入れる
3. Landing Page を作る。**資格情報を保存するかは合意事項**
4. Users & Groups を部署ごとに分ける
5. Campaign を作成して送信

## 4. 見る指標

| 指標 | 意味 |
|---|---|
| **報告率** | 担当窓口へ報告した割合。**最重要** |
| 初報までの時間 | 1 通目の報告が届くまでの分数 |
| クリック率 | 参考値。これだけを目標にしない |
| 入力率 | 資格情報を入力した割合 |
| 技術的検知 | メールゲートウェイ・EDR が止めた数 |

## 5. 終了後

1. ただちに種明かしを行い、見分け方を具体例つきで共有する
2. 報告した人に感謝を伝える（次回の報告率に直結します）
3. 検知できなかった技術的な経路を洗い出し、改善項目にする
4. 収集した資格情報があれば、合意した期間内に破棄し、破棄の記録を残す

## 報告書に書くこと

個人名は出さず、部署単位の数値と、組織として直すべき点（報告経路の周知、メールゲートウェイの設定、多要素認証の方式）を書きます。
OTP 方式の多要素認証を使っている場合は、中継型フィッシングで回避できることと、FIDO2 / WebAuthn への移行を併記してください。
